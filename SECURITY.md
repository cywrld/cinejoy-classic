# Cywrld security notes

This is practical hardening, not a security certification. No site can be promised unhackable. The static pages and Supabase/Stripe integrations have not been penetration-tested or live-tested against a configured project; review the SQL and function changes in a staging project before production.

## Current safeguards

- Browser configuration in `supabase-config.js` contains only blank placeholders and public client settings. Supabase anon/publishable keys are public; `service_role`, Stripe secret, Stripe webhook, OAuth client, and Resend keys belong only in Supabase server secrets.
- Admin authorization uses trusted Supabase `app_metadata.cinejoy_admin`, provisioned by an authorized project owner. User-editable metadata is not used. `admin.html` is a separate route, not linked from public navigation; its URL is not a security boundary. Auth and RLS enforce access.
- Database constraints, RLS policies, security-definer functions with an empty `search_path`, and database triggers protect catalog writes, private message ownership, product administration, audit rows, and entitlement creation. Browser roles cannot write payment orders, webhook receipts, or entitlements.
- Movie, review, message, and admin values rendered as HTML are escaped or inserted through text nodes. Contact/messages and reviews have server-side length checks and per-account database rate limits. Reviews require sign-in and are limited to one per account per film. New Auth accounts are not admins.
- Movie posters accept PNG/JPEG/WebP only, have a 250 KB bucket limit, and are uploaded only by admins. Digital deliverables are limited to ZIP/PDF/EPUB and 100 MB in a private bucket; the download function checks the signed-in buyer's server-recorded entitlement and returns a 60-second signed link. Do not upload encrypted archives or executables; scan archive contents for malware and verify distribution rights before upload. Storage MIME/size checks are not antivirus scanning.
- Checkout is off by default in browser configuration and independently requires server-side Stripe enablement and secrets. The server accepts only a published product ID, retrieves the configured Stripe one-time Price, and checks active status, currency, and amount against the database before creating hosted Checkout. The signed Stripe webhook validates timestamp/signature, order/user/product metadata, session ID, paid status, amount, and currency before recording an entitlement. The browser never grants access based on the success redirect.
- Audit records are generated by database triggers and have no browser update/delete grants. Private message bodies and payment secrets are not copied to the audit details.
- The optional site assistant is deterministic, uses bundled local files, and sends no prompts to a model provider.

## Deployment checklist

- [ ] Serve every page over HTTPS. Configure the exact HTTPS origin in Supabase Auth redirect allow-lists and the server-side `CINEJOY_SITE_URL`.
- [ ] Apply and review `supabase-setup.sql` in a new Supabase project. Test RLS using anon, normal authenticated, administrator, and service roles; never rely on hidden buttons.
- [ ] Provision the first administrator by editing `auth.users.raw_app_meta_data` in the Supabase dashboard/SQL Editor as the trusted owner. Never add an admin self-service role toggle.
- [ ] Enable Auth email-confirmation, CAPTCHA/bot protection and provider rate limits appropriate for the deployment. Database limits reduce per-account abuse but do not stop account farming or distributed attacks.
- [ ] Keep all private keys in Supabase Edge Function Secrets. If a key was exposed in chat, shell history, or a repository, revoke it and issue a replacement before deployment.
- [ ] Leave `payments.checkoutEnabled` and `STRIPE_CHECKOUT_ENABLED` off until the test-mode checkout, signed webhook, private file bucket, and purchase flow all pass. Test duplicate webhook delivery and delayed payment behavior.
- [ ] Upload only original or explicitly licensed content. Scan product files with a trusted malware scanner before uploading. The app does not perform malware scanning or determine copyright status.
- [ ] Run a secret scan before publishing. Confirm `.env*` files and `videos/*.mp4` are ignored, inspect every staged file, and ensure no service-role, Stripe, Resend, OAuth-client, or personal credentials are included. Never commit generated customer data or signed download links.
- [ ] Keep dependencies current and review/pin the Supabase browser client version when preparing a production release.

## Recommended HTTPS response headers

Set headers at the chosen static host/CDN. Host configuration differs, so the project does not claim these headers are already active. Replace `<PROJECT_REF>` with the real Supabase project reference and test Auth, storage images, downloads, and OAuth before enforcing the policy:

```text
Content-Security-Policy: default-src 'self'; base-uri 'self'; object-src 'none'; frame-ancestors 'none'; form-action 'self' https://<PROJECT_REF>.supabase.co; script-src 'self' https://cdn.jsdelivr.net; style-src 'self'; img-src 'self' data: blob: https://<PROJECT_REF>.supabase.co; media-src 'self' blob:; connect-src 'self' https://<PROJECT_REF>.supabase.co wss://<PROJECT_REF>.supabase.co; font-src 'self'; upgrade-insecure-requests
X-Content-Type-Options: nosniff
Referrer-Policy: strict-origin-when-cross-origin
Permissions-Policy: camera=(), microphone=(), geolocation=()
X-Frame-Options: DENY
```

Add HSTS only after the domain is fully HTTPS, including every subdomain covered by the policy. CSP and CORS are browser controls; they do not replace server-side authentication, RLS, webhook verification, or input validation.

## Remaining limits

The site has no configured Supabase project, Stripe account, production secrets, malware scanning service, or live operator account in this folder. Checkout and online features remain unavailable until configured. The admin-provided Stripe Price ID and metadata are still operator-managed configuration and should be reviewed. Public product/movie descriptions remain user-visible content; moderators should remove abusive or misleading listings. Contact and rating limits are per account and require Auth anti-abuse controls to resist multiple-account attacks.
